Digital twins

A digital twin predicts what a change or a failure does to a network before the network sees it. CANAH asks the twin in use through one contract, so any twin that speaks it can be used: netwins, or your own. Changing the twin takes effect at the next question; the agent's tools stay the same.

Add a custom twin

admin

A token is the name of an environment variable on CANAH's host, never the token itself.

The contract: canah.twin/1

Any twin answers four calls, in-process or over HTTP:

GET /twindescribe: name, version, domains (what each answers, its KPIs, an example scenario, fidelity, what it does not model), capabilities
POST /twin/validate{scenario} → ok, problems
POST /twin/predict{scenario} → decision (propose, reject, gather_more_data, met, not_met), probability and interval, trust tier, figures per entity and KPI, the change that ran, what is not modelled
POST /twin/check_writeoptional: a controller write tried before it is sent → propose, reject, ask_operator, … (the write gate uses it)
POST /twin/extraoptional: the twin's own read-only helpers, listed by describe

The full text: docs/TWIN_CONTRACT.md. A minimal twin to start from: examples/custom_twin.py.
